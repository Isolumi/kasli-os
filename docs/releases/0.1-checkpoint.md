# Kasli 0.1 Checkpoint

Date: 2026-05-04

This checkpoint records the first usable Kasli prototype. The code package
version is `0.1.2`; use `v0.1.2` for a release tag unless the project version is
changed before tagging. It is still reasonable to describe this milestone as
"0.1" in prose.

## What Works

- Local daemon: `kaslid`.
- Installed CLI: `kasli`.
- Unix domain socket daemon boundary with owner-only socket behavior.
- Append-only JSONL audit logging.
- Trusted read-only policy broker.
- Bounded, redacted evidence before model calls.
- Fedora RPM packaging through CPack.
- Installed CLI autostarts the user daemon when the default socket is missing or
  stale.
- Optional model answering with Ollama or LM Studio/OpenAI-compatible local
  servers.

Implemented read-only tools:

- `system.info`
- `disk.usage`
- `hardware.summary`
- `network.summary`
- `power.status`
- `packages.recent_changes`
- `packages.list`
- `systemd.units.list`
- `systemd.unit.status`
- `services.failed`
- `services.enabled`
- `journal.query`
- `service.diagnose`

## Verification

Verified on Fedora Linux 43 KDE:

```sh
ctest --test-dir build-fedora --output-on-failure
# 100% tests passed, 0 tests failed out of 160

kasli --tools-list
# returned ok=true with the full read-only tool registry

kasli --ask "what os is this?" --ask-tool system.info
# returned ok=true and answered Fedora Linux 43 from system.info evidence
```

Runtime model setup at checkpoint:

- Official Ollama service: active
- `ollama --version`: `0.23.0`
- Model: `gemma4`

Known model setup caveat:

- Fedora's distro-packaged `ollama-0.9.4-4.fc43` reported version `0.0.0` and
  failed to load `gemma4` with an unknown architecture error.
- Official Ollama `0.23.0` fixed the runtime path during local testing.

## Next Recommended Work

Build the next user-facing ergonomics slice before adding mutation.

Recommended scope:

- Natural `kasli ask` flow that can select safe read-only tools automatically
  for common questions.
- `kasli doctor` setup diagnostics for daemon status, socket reachability,
  model provider configuration, model availability, and known bad Ollama builds.
- Clear non-JSON user-facing error messages for common setup failures.

Backend state snapshots remain useful, but they should follow the ergonomics
work unless the next milestone explicitly shifts back to backend architecture.
